# plan-generator-bot

Telegram-бот (webhook) для учителя: составляет краткосрочные (поурочные) планы уроков в DOCX.
Quarkus 3 / Java 21, Postgres (Neon) + Flyway, OpenAI через Quarkus LangChain4j (структурированный ответ в Java-record), Apache POI для DOCX.

## Правила

- **Не писать тесты вообще**: ни unit, ни smoke, ни интеграционные, ни с Testcontainers. Не создавать `src/test`, не добавлять тестовые зависимости и не запускать `mvn test` / `verify`.
- **Не использовать Testcontainers / Dev Services**: `quarkus.devservices.enabled=false`. БД берётся из env (`DB_URL`, `DB_USER`, `DB_PASSWORD`).
- **Не делать запросов к платным API ради проверок**: никаких тестов и скриптов, которые напрямую обращаются к OpenAI по `OPENAI_API_KEY` (генерация планов, загрузка страниц книги, пробные вызовы модели), чтобы не тратить баланс. Это касается и разовых «проверочных» запусков. Единственное исключение: загрузка книг через `tools/book-ingest` и вызовы, которые пользователь явно просит выполнить сам. Перед любым платным вызовом сначала спросить и назвать примерную стоимость.
- Проверка работоспособности: сборка (`./mvnw -DskipTests package`) и ручной прогон бота без обращений к платным API (локально с фиктивным токеном бота и тестовым пользователем, без генерации).
- Секреты (`BOT_TOKEN`, `OPENAI_API_KEY`, пароль БД) только в `.env` (он в `.gitignore`) или в env хостинга. Не коммитить и не печатать в ответах.
- Не использовать популярные порты: локально порт из `.env` (`PORT`), по умолчанию 3847.

## Структура (`dev.ydt.plangen`)

- `webhook/WebhookResource`: `POST /webhook`, проверка секрета, whitelist `ALLOWED_IDS`, дедуп `update_id`, всегда 200.
- `bot/`: `Router` (команды и callback'и), `ProfileFlow` (ФИО, школа, предмет, язык, минуты), `ClassesFlow`, `ScheduleFlow`, `PlanFlow` (сбор данных урока и фоновая генерация), `InputParser` (вставка «Раздел: / Тема: / Цели:»).
- `llm/`: `LessonPlanner` (AI-сервис), `LessonContent` (схема ответа модели), `PlanService` (валидация: сумма минут = длительность урока, один повтор, локальная починка).
- `doc/`: `PlanDocx` (шаблон документа, чёрные линии), `Labels` (подписи ru / kk / en), `FileNames` (имя файла `plan-дата-класс-тема.docx`, ASCII).
- `llm/ProgramValue`: шесть ценностей программы «Біртұтас тәрбие» (enum, в схеме для модели это закрытый список). Модель выбирает одну по содержанию урока, документ печатает её жирным в строке «Құндылық мақсаты». В промпте также требование: минимум одно ИИ-задание в середине урока и ИИ в ресурсах.
- `telegram/`: DTO, REST-клиент Bot API, `Messenger`.
- `domain/`: Panache-сущности. БД-схема `plangen`, миграции в `src/main/resources/db/migration/` (новые изменения только новыми `V*__*.sql`).
- Промпты: `src/main/resources/prompts/lesson-system.txt` и `lesson-user.txt` (Qute: переменные в `{...}`, других фигурных скобок в тексте быть не должно). Всё, что уходит модели (промпты, описания схемы, замечания при повторе, пожелания-кнопки), пишется **на английском**: так меньше токенов. Язык самого плана задаётся переменной `{language}`.

## Учебники

- `tools/book-ingest` — отдельная утилита (свой pom, вне Docker-сборки бота). Грузит PDF в таблицы `books` и `book_pages`: один вызов vision-модели на страницу, структурированный JSON (печатный номер, упражнения, ключи, описания картинок). Цена и ключи см. в README.
- `domain/Book`, `domain/BookPage`, `service/BookService` (номера страниц, поиск по теме по словам без эмбеддингов, блок контекста для промпта), `bot/BookFlow` (шаг в /plan: книга → страницы → ещё книга).
- Каталог: `bot/CatalogFlow` (/books, добавление по ссылке okulyk.kz, привязка класс↔книга `class_books`, запрос загрузки и одобрение владельцем через `ADMIN_IDS`), `service/OkulykClient` (разбор одной страницы книги; хост только okulyk.kz/okulyk.com; PDF сервер НЕ скачивает). Статусы книги: catalog → requested → approved → loading → loaded | failed. Загрузку одобренных книг делает только `tools/book-ingest --watch/--once/--book-id` на компьютере владельца.
- В /plan сначала предлагаются загруженные книги, привязанные к выбранным классам (`Book.linkedLoaded`), иначе книги по классу.
- Книги фильтруются по классу, направлению класса (10–11) и четверти урока (по месяцу); тип книги: student_book / workbook. У плана сохраняется `book_refs` (JSON), чтобы «Другой вариант» брал те же страницы.
- Данные страницы берутся из `content_json` как есть; в промпте (п. 13) модель обязана цитировать упражнения со страницей и писать ключи ответов дословно.

## Конфиг (env)

`BOT_TOKEN`, `WEBHOOK_SECRET`, `ALLOWED_IDS`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `APP_TIMEZONE`, `DB_URL`, `DB_USER`, `DB_PASSWORD`, `PORT`. Дневного лимита на планы нет (защита от перерасхода только hard limit в панели OpenAI). Пример: `.env.example`.
Логи и расход: `LOG_LEVEL` (INFO по умолчанию), `OPENAI_LOG_REQUESTS=true` (сырые промпты и ответы), `PRICE_INPUT_PER_M` / `PRICE_OUTPUT_PER_M` (цены модели за 1 млн токенов, нужны только для оценки стоимости в логах). В логах: `[job]`, `[usage]` (токены и оценка за день), `[docx]`, `LLM attempt`. Токены и число попыток сохраняются в `lesson_plans`.

## Важно про JSON

Ответ модели парсится Jackson'ом, у которого глобально включён `SNAKE_CASE` (нужен для Telegram). Records с ответом модели (`LessonContent`, `Stage`) помечены `@JsonNaming(LowerCamelCaseStrategy)`: схема для модели строится из имён полей в camelCase, без этой аннотации многословные поля прочитаются как null. Новые records для ответа модели помечать так же.

## Соглашения

- `callback_data` в Telegram ≤ 64 байт: короткие id (`pl:c:12`, `cls:del:3`).
- Состояние диалога хранится в `conv_state` (инстанс может засыпать или перезапускаться).
- Цели обучения и коды вставляются в документ дословно так, как их прислал учитель. Модель пишет только цели урока и ход урока.
- Генерация идёт в фоновом потоке без открытой DB-транзакции; результат сохраняется через `QuarkusTransaction.requiringNew()`.
- Все сообщения бота — обычный текст (без parse mode).
